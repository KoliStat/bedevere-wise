# Bedevere Backend Protocol

**Status**: reference, v1.0
**Source of truth (TS)**: [`src/data/ipc/types.ts`](../src/data/ipc/types.ts)
**Companion plan**: bedevere-desktop's [`PROJECT_PLAN.md`](../../kolistat/bedevere-desktop/PROJECT_PLAN.md) (the
original design rationale; lives in the C++ shell repo since the
desktop host was the first implementer)

---

## 1. Overview

A host process — the original target was bedevere-desktop's C++ shell;
the protocol generalizes to any host (a `pip install bedeverer-py`
kernel, an R session, a remote relay) — and the Bedevere webview
renderer exchange RPC requests, RPC responses, server-pushed events,
and Arrow IPC streaming bytes over a **single localhost WebSocket
connection**. JSON travels in text frames; Arrow chunks travel in
binary frames prefixed with an 8-byte routing header.

This document is the canonical wire reference. The TypeScript
declarations in [`src/data/ipc/types.ts`](../src/data/ipc/types.ts)
mirror every shape called out here; the [`Bridge`](../src/data/ipc/bridge.ts)
+ [`IpcBackend`](../src/data/IpcBackend.ts) classes are the renderer-
side reference implementation. Host implementations bind their engine
to the wire shapes.

The protocol was originally born inside bedevere-desktop as
`ipc-protocol.md`. It moved to bedevere-wise in v0.13 alongside the
Backend abstraction (see [`feature/backend-abstraction`](../CHANGELOG.md))
so the contract has a single home and a versioning home that's
independent of any particular host implementation.

## 2. Transport

### 2.1 Socket lifecycle

1. **Shell startup**: bind a `websocketpp` server to `127.0.0.1:0` (OS-
   assigned port). Generate a 32-byte cryptographic random token; base64-
   encode it (URL-safe, no padding). Resolve the bound port via
   `acceptor::local_endpoint()`.
2. **Webview launch**: the shell injects the IPC parameters *out of band* —
   as a frozen JS global evaluated before the page's own scripts
   (`webview::init`), not in the URL:

   ```js
   window.__BEDEVERE_IPC__ = Object.freeze({ port: <n>, token: "<base64>" });
   ```

   The navigation URL carries only the (non-secret) port as a fallback
   (`…/index.html?ipcPort=<n>`; dev mode points at
   `http://localhost:5173?ipcPort=…`). Keeping the token out of the URL
   stops it leaking via referrer headers, webview diagnostic logs, or the
   address bar / DevTools network panel.
3. **Renderer connect**: on boot the renderer reads `window.__BEDEVERE_IPC__`
   (falling back to the `ipcPort` query param for the port) and opens
   `ws://127.0.0.1:<n>/`. The token is asserted on the first JSON frame
   (see §2.3).
4. **Server validates** the upgrade, then the token:
   - **Handshake** (`validate` handler): the upgrade is rejected unless the
     `Host` header names the loopback interface on our port
     (`127.0.0.1:<n>` or `localhost:<n>`) **and** the `Origin` header is the
     bundled webview (`file://…`, `null`, or absent) or the dev Vite origin.
     See §2.2.
   - **First frame**: constant-time compare of `auth` against the in-memory
     token. On mismatch the server sends close `4401` `UNAUTHORIZED`; no
     further frames are accepted. On match it transitions to dispatching.
5. **Steady state**: bidirectional text + binary frames flow until either
   side closes the connection. The shell tears down the WebSocket server on
   app exit; the renderer tears down on `window.beforeunload`. Inbound
   frames are capped (32 MB) and in-memory uploads are bounded per session.

### 2.2 Security model

- **127.0.0.1 binding only.** Never `0.0.0.0`. Same-machine same-user
  isolation is the threat model.
- **32-byte random token.** Generated by the shell at startup (libsodium
  `randombytes_buf`), base64-encoded, never logged, in-memory only (a fresh
  one is minted per launch). Required on the first frame of every
  connection — without it, any local process can scrape the port out of the
  OS connection table and read the dataset.
- **Token delivered out of band.** Injected as `window.__BEDEVERE_IPC__`
  (see §2.1); never placed in the navigation or `ws://` URL, so it can't
  leak through referrer / logs / the address bar.
- **Origin + Host validation on the upgrade.** The shell rejects the
  handshake unless `Host` names the loopback interface on our port and
  `Origin` is the webview (`file://`/`null`/absent) or the dev Vite origin.
  This defeats DNS-rebinding (a rebinding attacker's browser still sends the
  attacker's own hostname in `Host`) and stops an unrelated page the user
  has open from driving the engine. It is defense-in-depth layered on the
  token, not a replacement. Webviews vary in how they populate `Origin`
  (WebView2 / WKWebView / WebKitGTK differ); a host whose webview emits an
  unexpected origin must add it to the allowlist in `websocket_server.cpp`.
- **DevTools** (webview debug mode) is compiled in for dev builds only, so a
  packaged build doesn't expose the injected token via the inspector.

### 2.3 Auth frame format

The renderer asserts the token as a top-level `auth` field on the first JSON
frame it sends:

```jsonc
{ "id": "boot-001", "method": "getProtocolVersion", "auth": "<base64-token>" }
```

The shell accepts the first frame only if `auth` matches (constant-time).
Subsequent frames need not repeat `auth`; the validated connection is
trusted for its lifetime.

> Earlier revisions also sent the token as a `?token=…` query parameter on
> the `ws://` URL; that's been dropped now the token is delivered out of band
> (§2.1) — the `auth` frame is the sole carrier. A future revision could move
> it into a `Sec-WebSocket-Protocol` subprotocol handshake; that's a
> forward-compatible v1.x change.

### 2.4 Reconnect policy

There is no reconnect logic in v0. The shell is single-process; if the
WebSocket closes, the renderer surfaces a fatal modal and the user restarts
the app. Reconnect with session resumption is a v1.x candidate.

## 3. Frame envelopes

### 3.1 JSON request (renderer → shell)

```jsonc
{
  "id": "<string, renderer-chosen, non-empty>",
  "method": "<one of §5 methods>",
  "params": { /* method-specific; absent or {} when no params */ }
}
```

`id` MUST be unique across in-flight requests on this connection; the shell
echoes it in the response. Recommended: `crypto.randomUUID()`.

### 3.2 JSON response success (shell → renderer)

```jsonc
{
  "id": "<request id>",
  "ok": true,
  "result": { /* method-specific */ }
}
```

### 3.3 JSON response error (shell → renderer)

```jsonc
{
  "id": "<request id>",
  "ok": false,
  "error": {
    "code": "INVALID_PARAMS",
    "message": "fetchData: end must be >= start"
  }
}
```

`code` is one of the strings in §7. `message` is a human-readable
explanation suitable for logging; the renderer should branch on `code`,
not on parsed `message`.

### 3.4 JSON event (shell → renderer, unsolicited)

```jsonc
{ "event": "<tag>", /* event-specific fields */ }
```

Events are not correlated with any `id`. v1.0 defines a single event:

```jsonc
// success
{ "event": "streamEnd", "streamId": 42, "ok": true }

// failure (e.g. DuckDB threw mid-stream)
{
  "event": "streamEnd",
  "streamId": 42,
  "ok": false,
  "error": { "code": "DUCKDB_ERROR", "message": "Out of memory while spilling" }
}
```

See §4 for the renderer's obligations when `ok: false` arrives.

### 3.5 Binary frame (shell → renderer)

```
+----------------+----------------+-------------------------------+
| streamId u32le | chunkIndex u32le |   Arrow IPC streaming bytes  |
+----------------+----------------+-------------------------------+
^---- 8-byte header ----^---- payload (concatenable per stream) ---^
```

- `streamId`: u32 little-endian; the value the shell returned in the RPC
  response that initiated this stream. Server-allocated, monotonic, starts
  at 1. The value `0` is reserved and MUST NOT appear on the wire.
- `chunkIndex`: u32 little-endian; 0-based index within this stream. v1.0
  guarantees in-order delivery (TCP + single WebSocket connection), so a
  conformant renderer MAY ignore the field. It's present so a future
  multiplexed transport can reorder.
- Payload: the renderer concatenates payloads for a given `streamId` in
  `chunkIndex` order to obtain a valid Arrow IPC **streaming format** byte
  sequence (schema message first, then any number of dictionary + record
  batch messages, then end-of-stream marker as per the Arrow spec).

There is no per-chunk Arrow framing differentiator inside the payload — the
shell writes one `RecordBatchStreamWriter` per `streamId` and slices its
output bytes into chunks at the WebSocket frame boundary. Concatenation
rebuilds the Arrow stream verbatim.

## 4. Stream lifecycle

1. Renderer issues a row-returning RPC (`fetchData`, `fetchDataColumnRange`,
   `executeQuery` on a SELECT). The shell allocates the next free
   `streamId` (monotonic u32, starts at 1) and returns it in the JSON
   response.
2. Shell pushes binary frames tagged with that `streamId`. The renderer
   buffers payloads per `streamId`.
3. Shell sends a `streamEnd` event when the Arrow stream finishes. The
   renderer THEN flushes the buffered bytes through
   `apache-arrow`'s `tableFromIPC` (or `RecordBatchStreamReader.from(…)`
   for partial-paint flows in a future iteration).
4. On `streamEnd: { ok: false }` the renderer MUST:
   - Discard every buffered payload for that `streamId` (treat the partial
     table as invalid).
   - Reject the awaiting promise with the embedded `error`.
   - Never deliver a partial `Table` to the UI layer.
5. There is no cancellation in v1.0 — once a stream is opened the renderer
   awaits its terminal event. See §10 for the v1.x cancellation proposal.

Per-stream invariants the shell guarantees:

- A `streamId` is single-use. The shell never reuses an id within a single
  WebSocket connection.
- A `streamEnd` is always sent, even on error.
- Chunks for distinct `streamId`s may interleave on the wire (multiplex).
- The first chunk of every stream begins with Arrow IPC's schema message.

## 5. Method catalog

Each method below documents `params`, the `result` shape on success, and
the `code` values it may surface on failure. Where the result rides the
binary channel, the JSON `result` carries the `streamId` to await.

### 5.1 Data methods

#### 5.1.1 `getMetadata`

Retrieve dataset-level metadata for a registered table.

```jsonc
// params
{ "table": "adsl" }
// result — see WireDatasetMetadata in types.ts
{
  "name": "adsl",
  "alias": "ADSL",
  "fileName": "adsl.sas7bdat",
  "totalRows": 1234,
  "totalColumns": 17,
  "columns": [/* WireColumn[] */]
}
```

Errors: `NOT_FOUND` (no such table), `INVALID_PARAMS`.

#### 5.1.2 `fetchData`

Fetch a row range over the binary channel.

```jsonc
// params — `end` is exclusive
{ "table": "adsl", "start": 0, "end": 100 }
// result — rows ship as Arrow on streamId
{ "streamId": 7, "totalRows": 1234 }
```

`totalRows` reflects the full table cardinality (NOT the slice size), so
the renderer can size its virtual scrollbar without a second round-trip.

Errors: `NOT_FOUND`, `INVALID_PARAMS` (e.g. negative bounds, `end < start`),
`DUCKDB_ERROR`.

#### 5.1.3 `fetchDataColumnRange`

Same as `fetchData` but restricted to a column slice; useful for the
spreadsheet's horizontal virtualization.

```jsonc
// params
{
  "table": "adsl",
  "start": 0,
  "end": 100,
  "startCol": 0,
  "endCol": 8
}
// result — Arrow stream contains only the requested columns
{ "streamId": 8, "totalRows": 1234 }
```

Errors: as `fetchData`, plus `INVALID_PARAMS` on bad column bounds.

#### 5.1.4 `getColumnStats`

Compute stats over the unfiltered column source. Drives filter-UI bounds.

```jsonc
// params
{ "table": "adsl", "column": "AGE" }
// result — WireColumnStats | null
```

`null` is returned for columns whose `dataType` is `complex` (struct, list,
map) or `binary` where stats are not meaningful.

Errors: `NOT_FOUND` (no such column), `DUCKDB_ERROR`.

#### 5.1.5 `getColumnStatsFiltered`

Same shape as `getColumnStats`, plus an optional filter IR applied before
stats compute. Drives the side-panel display (mean/median/sd/histogram).

```jsonc
// params
{
  "table": "adsl",
  "column": "AGE",
  "filter": [
    { "columnName": "SEX", "filterType": "include", "values": ["F"] }
  ]
}
// result — same shape as getColumnStats
```

Errors: as `getColumnStats`, plus `INVALID_PARAMS` if the filter IR is
malformed.

#### 5.1.6 `searchColumnValues`

Distinct-value lookup with substring or regex matching. Always queries the
unfiltered source.

```jsonc
// params
{
  "table": "adsl",
  "column": "SITE",
  "query": "PARI",
  "mode": "substring",
  "limit": 50
}
// result
[
  { "value": "PARIS-1", "count": 84 },
  { "value": "PARIS-2", "count": 31 }
]
```

Errors: `NOT_FOUND`, `INVALID_PARAMS` (bad regex when `mode === "regex"`).

### 5.2 DataProvider mutators

The `DataProvider` interface declares `setName`, `setDescription`, and
`setLabel` as synchronous void methods. The renderer's `IpcDataProvider`
implements them as fire-and-forget local updates AND as RPC calls so the
shell's server-side dataset registry stays in sync when the user renames a
table or attaches a description in the UI.

All three return an empty success result; they're idempotent.

#### 5.2.1 `setName`

```jsonc
{ "table": "adsl", "name": "adsl_v2" }
// result: {}
```

The shell updates its in-memory table-name index. SQL aliasing is the
user's job (via `executeQuery` issuing `ALTER TABLE … RENAME TO …`).

Errors: `NOT_FOUND`, `INVALID_PARAMS` (e.g. name collision).

#### 5.2.2 `setDescription`

```jsonc
{ "table": "adsl", "description": "Subject-level analysis dataset." }
// result: {}
```

Errors: `NOT_FOUND`.

#### 5.2.3 `setLabel`

```jsonc
{ "table": "adsl", "label": "Analysis Data Subject Level" }
// result: {}
```

Errors: `NOT_FOUND`.

### 5.3 Session methods

#### 5.3.1 `registerFile`

Open a file path with the appropriate DuckDB reader (`read_parquet`,
`read_csv_auto`, `read_sas`, …) and bind it as a table in the session.

```jsonc
{ "path": "/abs/path/file.parquet", "tableName": "adsl" }
// result
{ "tableName": "adsl", "totalRows": 1234, "totalColumns": 17 }
```

The optional `sheet` param picks a worksheet of a multi-sheet `.xlsx`
workbook. When present and non-empty, the host emits
`read_xlsx('<path>', sheet='<sheet>')` (single-quote-escaping the sheet
name); every non-xlsx reader ignores it. This is how the desktop
imports a chosen Excel sheet — its file-tree sheet nodes carry the
parent workbook's `path` plus the `sheet` name, since the bytes never
cross the wire for picker-opened files.

```jsonc
{ "path": "/abs/path/book.xlsx", "tableName": "adsl_summary", "sheet": "Summary" }
// result
{ "tableName": "adsl_summary", "totalRows": 1234, "totalColumns": 17 }
```

The host MUST confine `path` to the file-access grant ledger (a file the
user opened via the native picker, or one beneath a picked folder); a
path outside it is rejected with `NOT_FOUND`. This stops a peer that
reached the sidecar from registering an arbitrary file the user can read.

Errors:

- `NOT_FOUND` — path does not resolve, or is outside the grant ledger
- `DUCKDB_ERROR` — reader failed (corrupt file, unsupported extension)
- `INVALID_PARAMS` — `tableName` is empty or contains illegal characters
- `UNLICENSED` — file format requires a commercial reader extension the
  user has not licensed (e.g. future paid format support)

#### 5.3.1a `readFile`

Return the raw bytes of a host file, **base64-encoded** in the JSON
result. The renderer uses this when a file-tree node carries a host
`path` (folder / file picker) instead of browser bytes, but a JS-side
reader must parse the file itself — notably `.xlsx` worksheet
enumeration, which unzips `xl/workbook.xml` in the renderer to list
sheet names. Bulk data files do NOT use this; they import via
`registerFile` by path so the host reads them directly and the bytes
never travel the wire.

```jsonc
{ "path": "/abs/path/book.xlsx" }
// result
{ "data": "<base64 of the file bytes>" }
```

Confinement is identical to `registerFile`: the host MUST reject a
`path` outside the file-access grant ledger with `NOT_FOUND`, so this
can't be used to exfiltrate arbitrary files. The host MUST also bound
the size (the reference host caps a single read at 256 MiB, refusing
larger files with `INVALID_PARAMS`) so a huge file can't exhaust host
memory or overflow the response frame.

Errors:

- `NOT_FOUND` — path does not resolve, or is outside the grant ledger
- `INVALID_PARAMS` — `path` missing/empty, or file exceeds the size cap
- `INTERNAL` — I/O failure opening or reading the file

#### 5.3.2 `executeQuery`

Execute arbitrary SQL. Row-returning statements ship results over the
binary channel; non-row statements report rows affected.

```jsonc
// params
{ "sql": "SELECT * FROM adsl WHERE AGE > 65" }
// result for SELECT
{ "streamId": 11, "totalRows": 142 }
// result for INSERT / UPDATE / DELETE / DDL
{ "affectedRows": 142 }
```

Errors: `SQL_ERROR` (parse / plan failure), `DUCKDB_ERROR` (runtime),
`UNLICENSED` (query references a function from a licensed extension that
was not loaded).

#### 5.3.3 `listTables`

Enumerate every table currently registered in the session.

```jsonc
// params: {}
// result
[
  { "name": "adsl", "totalRows": 1234, "totalColumns": 17 },
  { "name": "adae", "totalRows": 6789, "totalColumns": 24 }
]
```

Errors: `DUCKDB_ERROR`.

#### 5.3.4 `visualize`

Dispatch a `VISUALIZE … DRAW` statement through the `stats_duck` extension
and return the **fully-materialized** chart payload: the Vega-Lite spec
plus a dict of layer-name → row arrays. The shell executes each layer SQL
internally before responding; the renderer hands the result directly to
`ChartVisualizer.setSpec(spec, datasets)`.

This shape matches `runVisualize` from `@kolistat/bedevere-wise/ui`,
so a renderer with the package's `ChartVisualizer` mounted needs zero
translation.

```jsonc
// params
{ "sql": "VISUALIZE adsl DRAW point WITH (X = AGE, Y = WEIGHT)" }
// result
{
  "spec": { /* Vega-Lite spec object */ },
  "datasets": {
    "layer_0": [
      { "AGE": 42, "WEIGHT": 70.5 },
      { "AGE": 58, "WEIGHT": 82.1 }
      // ...
    ]
  }
}
```

Errors: `SQL_ERROR`, `DUCKDB_ERROR`, `UNLICENSED` (if a future commercial
extension provides the DRAW kind).

#### 5.3.5 `exportTable`

Write an entire table to a file in a binary/columnar format the renderer
can't serialize itself. The host pops a **native Save dialog** (so the
user picks the destination and gets the OS overwrite prompt), then runs
`COPY <table> TO '<path>' (FORMAT <format>)` against its DuckDB and
replies with the path it wrote — the bytes never travel the wire. (The
in-process WASM backend implements the same `Backend.exportTable` method
without this RPC: it COPYs to its virtual FS and hands the bytes to the
browser for download.)

`format` is one of `parquet` / `json` (DuckDB-native) or `xpt` / `sav` /
`por` / `sas7bdat` (the `stats_duck` COPY functions). The host MUST
allowlist `format` against a fixed set before interpolating it into SQL,
and quote the table + path. `filenameHint` is the dataset's display name,
used as the Save dialog's default filename. Dismissing the dialog yields
`{ "exported": false, "cancelled": true }` — a no-op, not an error.

```jsonc
// params
{ "table": "penguins", "format": "parquet", "filenameHint": "penguins" }
// result (saved)
{ "exported": true, "path": "C:\\Users\\me\\penguins.parquet", "rowsExported": 344 }
// result (user cancelled the Save dialog)
{ "exported": false, "cancelled": true }
```

Errors: `INVALID_PARAMS` (missing params / unknown format), `SQL_ERROR`,
`DUCKDB_ERROR` (e.g. a stat-format COPY function isn't registered because
`stats_duck` isn't loaded).

### 5.4 Plugin methods

#### 5.4.1 `getPluginCatalog`

Snapshot of every plugin in the compiled catalog with its runtime status.
Mirrors `PluginManager::describe_catalog()` in
`shell/plugins/plugin_manager.h`.

```jsonc
// params: {}
// result
[
  {
    "manifest": {
      "name": "stats_duck",
      "displayName": "Stats Duck",
      "version": "0.4.2",
      "description": "Statistical helpers, VISUALIZE … DRAW chart syntax, …",
      "licenseRequired": false,
      "dependsOn": [],
      "vendor": "Bedevere",
      "homepage": "https://github.com/KoliStat/the-stats-duck"
    },
    "status": "loaded"
  }
]
```

Errors: `INTERNAL`.

#### 5.4.2 `loadPlugin`

Attempt to load a single extension by name. Idempotent.

```jsonc
{ "name": "stats_duck" }
// result
{ "name": "stats_duck", "status": "loaded" }
```

Errors: `NOT_FOUND` (not in catalog), `UNLICENSED` (no covering token),
`DUCKDB_ERROR` (extension binary missing or rejected by DuckDB).

#### 5.4.3 `unloadPlugin`

Mark a plugin as "should not be loaded next session." The current DuckDB
connection retains the extension until process exit (see the comment in
`plugin_manager.h` for the rationale).

```jsonc
{ "name": "clinical_duck" }
// result
{ "name": "clinical_duck", "status": "licensed" }
```

The `status` in the response reflects what the plugin would be on next
launch — typically `"licensed"` for a previously-loaded commercial
extension whose token is still installed.

Errors: `NOT_FOUND`.

### 5.5 License methods

#### 5.5.1 `listLicenses`

Enumerate installed licenses. The raw signed JSON tokens are NOT
returned — only the verified summary needed for the License panel.

```jsonc
// params: {}
// result
[
  {
    "licenseId": "lic_01HRZ123",
    "extensions": ["clinical_duck"],
    "issuedTo": "user@example.org",
    "issuedAt": 1717372800,
    "expiresAt": 1748908800,
    "versionConstraint": "<=2.x"
  }
]
```

Errors: `INTERNAL`.

#### 5.5.2 `addLicense`

Install a license token. The shell parses the JSON, verifies the Ed25519
signature against the baked-in public key, and persists the file to the
OS config dir.

```jsonc
{ "token": "<full signed JSON token>" }
// result
{ "licenseId": "lic_01HRZ123", "extensions": ["clinical_duck"] }
```

Errors: `INVALID_SIGNATURE`, `EXPIRED`, `DUPLICATE`, `MALFORMED_TOKEN`.

#### 5.5.3 `removeLicense`

Remove an installed license by id. Idempotent w.r.t. the absence case
(returns `removed: false`); explicitly NOT an error to remove a non-
existent id.

```jsonc
{ "licenseId": "lic_01HRZ123" }
// result
{ "removed": true }
```

Errors: `INTERNAL`.

### 5.6 Meta

#### 5.6.1 `getProtocolVersion`

Sanity-check handshake. Renderer SHOULD call this immediately after
`connect` and refuse to proceed if `version` is not the value baked into
its build.

```jsonc
// params: {}
// result
{ "version": "1.0" }
```

Errors: none in normal operation; `INTERNAL` if the shell is degraded.

## 6. Wire-format reference

### 6.1 `WireDataType`

A string union. Accepted values (mirrors
`bedevere-wise/src/data/types.ts`):

```
BOOLEAN
TINYINT  SMALLINT  INTEGER  BIGINT  HUGEINT
UTINYINT USMALLINT UINTEGER UBIGINT UHUGEINT
FLOAT  DOUBLE  DECIMAL
DATE  TIME  TIME_TZ  TIMESTAMP  TIMESTAMP_TZ
TIMESTAMP_NS  TIMESTAMP_MS  TIMESTAMP_S  INTERVAL
VARCHAR
BLOB  BIT  UUID  JSON  ENUM
LIST  STRUCT  MAP  UNION
UNKNOWN
```

The shell's catalog mapping from DuckDB's `column_type` strings to
`WireDataType` MUST match the behaviour of `normalizeDuckDBType()` in
the upstream package. Parameterized types (`VARCHAR(255)`, `DECIMAL(10,2)`)
collapse to their base; compound temporal types
(`TIMESTAMP WITH TIME ZONE`, etc.) collapse per the upstream table.

### 6.2 `WireColumn`

```jsonc
{
  "name": "AGE",
  "key": null,              // primary-key marker or null
  "extra": null,            // freeform DuckDB extras column or null
  "default": null,
  "label": "Age (years)",   // optional, free-form display label
  "dataType": "INTEGER",
  "rawType": "INTEGER",     // unparameterized raw column_type string
  "hasNulls": false
  // Optional, omit if absent: `length` (number) and `format` (string
  // OR Intl.NumberFormatOptions literal). `null` is NOT a valid value
  // — emit the key only when there's a real value to set.
}
```

### 6.3 `WireDatasetMetadata`

```jsonc
{
  "name": "adsl",
  "alias": "ADSL",          // optional
  "fileName": "adsl.sas7bdat",  // optional
  "description": "...",     // optional
  "label": "...",           // optional
  "totalRows": 1234,
  "totalColumns": 17,
  "columns": [/* WireColumn[] */]
}
```

### 6.4 `WireColumnStats`

```jsonc
{
  "isCategorical": true,
  "totalCount": 1234,
  "nullCount": 12,
  "distinctCount": 7,
  "valueCounts":    [["Active", 800], ["Failed", 300], ["Withdrawn", 122]],
  "valueCountsRaw": [["Active", 0], ["Failed", 1], ["Withdrawn", 2]],
  "numericStats": {
    "min": 0, "max": 2, "mean": 0.45, "median": 0, "stdDev": 0.71
  },
  "temporalStats": null,
  "histogramEdges": null
}
```

Map fields are `[key, value][]` arrays. Pass through `new Map(arr)` to
rehydrate. `numericStats` is `null` for non-numeric columns;
`temporalStats` and `histogramEdges` are optional and absent when not
applicable.

### 6.5 `WireColumnStatsNumeric`

```jsonc
{ "min": 0, "max": 100, "mean": 42.5, "median": 41, "stdDev": 12.7 }
```

### 6.6 `WireColumnStatsTemporal`

```jsonc
{ "min": 19000, "max": 20100 }   // raw values (days for DATE, etc.)
```

> **OPEN_QUESTION: BigInt temporal values.** TIMESTAMP storage in DuckDB is
> microseconds since epoch (i64). Values from the 1970–2262 window fit in
> JSON's safe-integer range, but TIMESTAMP_NS can exceed it. v1.0 ships
> these fields as JSON numbers and trusts the dataset is in-range; if a
> NS-precision dataset breaks the bound, switch to dual-form `{ "min":
> "19000000000000000000", "minStr": "..."}` or `{ "min": [low32, high32] }`.
> Alternatives:
>   (a) Always string-encode temporal min/max — uniform but renderer must
>       parse before plotting;
>   (b) Tagged form per type — TIMESTAMP_NS uses string, others use number;
>   (c) Two fields `min` (number) + `minHigh` (number) for high 32 bits.
>
> Recommendation: defer until a real out-of-range dataset surfaces. The
> renderer currently round-trips `WireColumnStatsTemporal` straight into
> `Number` fields, so (a) is the cleanest forward-compatible upgrade.

### 6.7 `WireColumnFilter` (filter IR)

Mirrors `ColumnFilter` in
`bedevere-wise/src/data/ColumnFilterManager.ts`. The shape is stable per
the upstream comment, but the IR's evolution is owned by bedevere-wise;
the shell MUST accept (and may safely ignore) unknown forward-compatible
fields.

```jsonc
// Categorical include
{
  "columnName": "SEX",
  "dataType": "VARCHAR",
  "filterType": "include",
  "values": ["F", "M"]
}

// Numeric range
{
  "columnName": "AGE",
  "dataType": "INTEGER",
  "filterType": "range",
  "min": 18,
  "max": 65
}

// Temporal range — ISO strings
{
  "columnName": "VISITDT",
  "dataType": "DATE",
  "filterType": "range",
  "minStr": "2024-01-01",
  "maxStr": "2024-12-31"
}
```

A filter is a JSON array. The shell joins individual filters with
SQL `AND`.

> **OPEN_QUESTION: filter combinators.** The IR is implicit-AND of
> per-column predicates. There is no current way to express OR or to
> filter the same column with two predicates simultaneously. If those
> become user-facing requirements, the IR needs an explicit tree
> (`{ "op": "and", "children": [...] }` etc.). Recommendation: stay with
> implicit-AND in v1.0; upgrade IR in lockstep with bedevere-wise when the
> UI gains compound filters.

### 6.8 `WirePluginManifest`

Mirrors `bedevere::plugins::PluginManifest`. C++ `std::optional` fields are
JSON-optional (absent when empty).

```jsonc
{
  "name": "stats_duck",
  "displayName": "Stats Duck",
  "version": "0.4.2",
  "description": "...",
  "licenseRequired": false,
  "dependsOn": [],
  "vendor": "Bedevere",
  "homepage": "https://github.com/KoliStat/the-stats-duck"
}
```

### 6.9 `WirePluginStatus`

A string union mirroring `bedevere::plugins::PluginStatus` (lowered to
camelCase on the wire):

```
"available"   // bundled, eligible to load (free extensions before load)
"unlicensed"  // bundled, licenseRequired=true, no token covers it
"licensed"    // bundled, token in store, not yet loaded
"loaded"      // currently registered with DuckDB
"error"       // load attempt failed; see errorMessage on the runtime view
```

### 6.10 `WirePluginRuntimeView`

```jsonc
{
  "manifest": { /* WirePluginManifest */ },
  "status": "loaded",
  "errorMessage": null
}
```

`errorMessage` is populated only when `status === "error"`.

### 6.11 `WireLicense` (renderer view)

```jsonc
{
  "licenseId": "lic_01HRZ123",
  "extensions": ["clinical_duck"],
  "issuedTo": "user@example.org",
  "issuedAt": 1717372800,
  "expiresAt": 1748908800,        // or null for perpetual
  "versionConstraint": "<=2.x"    // optional
}
```

The raw signed JSON token is NOT included; the shell holds it for disk
round-trip.

### 6.12 `WireLicenseToken` (signed JSON token)

The full token format documented in
[`PROJECT_PLAN.md` §2.6](../PROJECT_PLAN.md). Fields use snake_case (as
issued by the offline signing tool); the renderer never inspects them
directly, but the shape is normative for the issuer:

```jsonc
{
  "license_id":  "lic_01HRZ123",
  "extensions":  ["clinical_duck"],
  "issued_to":   "user@example.org",
  "issued_at":   1717372800,
  "expires_at":  null,
  "version_constraint": "<=2.x",
  "signature":   "ed25519:<base64>"
}
```

The signature covers the canonical JSON serialization of the token with
the `signature` field removed.

> **OPEN_QUESTION: canonical-JSON algorithm.** PROJECT_PLAN §2.6 says
> "canonical JSON" but doesn't lock the algorithm. The likely candidates
> are RFC 8785 JCS (Canonical JSON for JSON Web Signatures) and a custom
> sort-keys-and-utf8 routine. Recommendation: RFC 8785 JCS — there's a
> reference implementation in C++ and the JS ecosystem (`canonicalize`
> on npm) interoperates with it; this lets the offline signing tool, the
> desktop verifier, and any future audit tool all agree on the bytes.
> Land this before the first commercial extension ships (PROJECT_PLAN §8
> Phase 6, Open Question #9).

## 7. Error code registry

`error.code` values the shell may emit. Listed canonically; renderers
SHOULD branch on `code`, MUST treat unknown codes as opaque generic
failures, and MUST display `error.message` to the user as-is for
diagnostics.

| Code                | Semantics                                                                                                   |
| ------------------- | ----------------------------------------------------------------------------------------------------------- |
| `UNAUTHORIZED`      | Auth handshake failed: missing or wrong token on the WebSocket query / first frame                          |
| `UNKNOWN_METHOD`    | `method` is not in the v1.0 catalog                                                                         |
| `INVALID_PARAMS`    | `params` failed shape, type, or range validation                                                            |
| `NOT_FOUND`         | Referenced table, column, `streamId`, plugin name, or license id does not exist                             |
| `DUCKDB_ERROR`      | DuckDB threw at runtime; `message` carries DuckDB's text                                                    |
| `SQL_ERROR`         | Parse / plan failure — a categorisable subset of `DUCKDB_ERROR`                                             |
| `UNLICENSED`        | A licensed extension is required (load, query, or registration) but no covering token is installed          |
| `INVALID_SIGNATURE` | Ed25519 signature on a license token did not verify against the baked-in public key                         |
| `EXPIRED`           | License token's `expires_at` is in the past                                                                 |
| `DUPLICATE`         | A license with the same `license_id` is already installed                                                   |
| `MALFORMED_TOKEN`   | License token JSON could not be parsed, or a required field is missing                                      |
| `NOT_IMPLEMENTED`   | Method is documented in v1.0 but the current shell build returns no result (Bucket B in PROJECT_PLAN §2.3)  |
| `INTERNAL`          | Shell-side error not attributable to user input (out of memory, I/O failure on config dir, programmer bug)  |

New codes may be added in minor versions; existing codes are immutable.

## 8. Arrow streaming details

- The shell uses `arrow-cpp`'s `RecordBatchStreamWriter` to serialize
  DuckDB query results into the Arrow IPC streaming format (schema
  message → optional dictionary messages → record batches → end-of-stream).
- The renderer concatenates binary-frame payloads for a given `streamId`
  in `chunkIndex` order. The concatenation IS a valid Arrow IPC stream
  byte sequence — no extra framing.
- The first chunk always contains the schema message; later chunks may
  contain a partial record batch and the renderer MUST NOT attempt to
  parse partial chunks individually. Wait for `streamEnd` before
  invoking `tableFromIPC`.
- For partial-paint flows (future), use `RecordBatchStreamReader.from(…)`
  with an async byte iterator fed by the chunk bucket; the reader emits
  one batch at a time as soon as enough bytes are buffered for a complete
  message.
- The shell SHOULD chunk on natural Arrow message boundaries (one
  RecordBatch per chunk) but is NOT required to. The renderer cannot rely
  on a chunk being a complete Arrow message; concatenation is the safe
  contract.

## 9. Versioning

- Wire protocol version: `1.0`.
- Renderer SHOULD call `getProtocolVersion()` immediately after `connect`
  and verify the response matches the version baked into its build. On
  mismatch the renderer surfaces a fatal modal directing the user to
  reinstall or update.
- Major version bump: any breaking change to JSON envelope shapes,
  binary-header layout, or method semantics.
- Minor version bump: adding methods, optional fields, or new error codes.
- The `version` string is the source-of-truth for compatibility decisions;
  do not rely on individual feature-detection probes for v1.0.

## 10. Open considerations (deferred to v1.x)

These are intentionally NOT implemented in v1.0; documented so the next
agent knows the shape of the future work.

1. **Stream cancellation.** Currently the renderer must await `streamEnd`
   for every stream it opens. A `cancelStream` method (`params: { streamId }`)
   plus a server-side abort hook on the `RecordBatchStreamWriter` would let
   the renderer drop irrelevant in-flight queries (e.g. user scrolled past
   the awaited page).
2. **Per-frame compression.** Arrow IPC streaming supports compressed
   record batches (LZ4 / Zstd). v1.0 ships uncompressed because the
   transport is localhost (negligible bandwidth win) and the CPU cost may
   exceed the savings. Revisit if Arrow batches become measurably I/O-
   bound under the WebSocket framing.
3. **Backpressure / flow control.** WebSocket has TCP-level backpressure
   only; the shell can swamp the renderer's event loop with binary
   frames if a render lags. A credit-based control frame
   (`streamWindow: { streamId, bytes }`) is the standard fix.
4. **Schema evolution.** v1.0 has no negotiated schema versioning beyond
   `getProtocolVersion()`. If a future extension adds optional
   `WireColumn` fields, renderers must tolerate them; a more rigorous
   approach is a per-message schema fingerprint.
5. **Concurrent connections.** v1.0 assumes one renderer per shell
   process. Multi-tab / multi-window setups need either multiple shell
   processes or a session-keyed message multiplexer.
